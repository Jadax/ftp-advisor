# FTP Advisor

Single-file Tampermonkey userscript: `ftp-advisor_user.js` (~6100 lines, one IIFE). Tactical/scouting advisor for fromthepavilion.org (cricket sim). Team is auto-detected per install (`getTeamId()`) — not hardcoded to any one team/user. No build step, no test suite, no other source files. Public repo: github.com/Jadax/ftp-advisor.

## Active Rules
- Keep the script modular; never duplicate a helper — grep for existing functions before adding one.
- No extensive explanatory prose in responses; output code/diffs directly, short summary only.
- Everything lives in `ftp-advisor_user.js` — don't create new files unless explicitly asked.
- Comments: only non-obvious WHY (hidden constraint, workaround, source of a magic number). Never WHAT.
- After any edit, verify with `node --check "ftp-advisor_user.js"` — the only available sanity check (no test suite, no build step, no headless access to the live game).
- Don't re-read the whole file to get oriented — grep/Glob the sections below by name.

## Ship workflow
Public repo, installed by other people. After a change is verified:
1. Bump `@version` in the metadata block (top of file).
2. `git add -A && git commit -m "vX.Y: <what changed and why>"`.
3. `git push` (origin already configured).
Do this for every shipped change unless told otherwise — there's no separate release process.

## Map (grep these, don't re-read the file)
- Lookup tables / constants: top of file — `SKILL_MAP`, `FATIGUE_MAP`, `PITCH_EFFECTS`, `AGE_SCOUT_THRESHOLDS`
- Age parsing: `parseGameAge(text)` (v8.9) — the ONE correct parser for the game's age text, used everywhere age is scraped (`parsePlayerRow`, `parseOpponentPlayerRow`, `parseTransferRow`, `scrapePlayerDetailPage`, the training-page scraper). The game shows age as years + a week count out of 14 (`"25.05"` in tables, `"25y5w"` in detail panels), NOT a base-10 decimal — `parseFloat("20.14")` reads 20.14 (14% into the year) when it's actually 14/14 = 21.0, a player who for scouting/training purposes has already turned 21. Every downstream `Math.round(player.age)` bracket check (age-scout thresholds, 16-20 curve, senior/aging training paths) is correct as-is once fed a true decimal age from this function — no separate rounding logic needed, JS's round-half-up already lands boundary weeks (7+/14) in the next age bracket.
- Team config (auto-detected): `getTeamId()`, `detectMyTeamIdFromPage()`
- Pro-tier scaffold — **exists but unwired, gates no feature**: `isProUser()`, `validateLicense()`
- AI-recommendations scaffold — **exists but unwired**: `buildAIContextSnapshot()`, `getAICentralRecommendation()`, `promptForAIKey()`. Key-storage approach is decided (user's own key, one-time prompt); `AI_ENDPOINT_URL` provider/endpoint is still a placeholder — needs that decision before wiring a UI trigger.
- Form/Experience multiplier curves (real game data, from `FTP_Training 5.2.xlsx`'s Form-Exp tab) — **live** (v8.16), wired into `calculateBattingScore()`/`calculateBowlingScore()` as `score *= formMult * expMult`, replacing the old flat additive form/experience terms: `FORM_MULTIPLIER`, `EXPERIENCE_MULTIPLIER`
- Training weekly-gain estimate (real data from the same workbook's "Base Level Training" table, combined with the pre-existing `ACADEMY_SPEED`/age/talent/slowdown multipliers) — **live**, shown as "~Nwk to next level" + a "📅 12wk outlook" line on Training page recs: `TRAINING_BASE_RATES`, `estimateWeeklyTrainingGain()`, `weeksToNextLevel()`, `simulateTrainingPlan()`, `formatTrainingOutlook()`. Does NOT read the workbook's own precomputed `DB!$DB$6:$GL$15` grid, so treat its output as a formula-based estimate consistent with the rest of the script, not a byte-identical reproduction of the spreadsheet.
- **14 weeks per age-year, not 52.** Official manual: "players age weekly, becoming one year older every fourteen weeks" — matches the workbook's own Wk0-Wk14-per-age-column layout exactly. Every simulated-age advancement in `simulateTrainingPlan()`/`simulateAdaptiveTrainingPlan()` uses `(week-1)/14`. This was `/52` until v8.5 — every multi-week projection before that understated aging by ~3.7x. If you add a new simulation that advances age, use 14, not 52.
- `getAcademySpeedForPlayer(player, academyInfo)` — the real, per-player academy training speed. Prefers the game's own live-scraped "Senior/Youth Training Efficiency %" (`parseAcademyDoc`'s `seniorEfficiency`/`youthEfficiency`, age-appropriate) over the derived `ACADEMY_SPEED` curve, since the official manual (`rules.htm?rulespage=training`) confirms senior and youth academy effectiveness are tracked separately by the game — a single curve can never capture that. Falls back to `ACADEMY_SPEED[levelNum]` only when the Academy page hasn't been visited/cached yet. Use this everywhere a specific player's training speed is needed; `ACADEMY_SPEED[level]` directly is still correct for level-to-level upgrade comparisons (hypothetical levels you don't have live data for).
- Adaptive multi-week training plan (`simulateAdaptiveTrainingPlan()`) — re-runs `recommendTraining()`'s real staged logic fresh every simulated week (fielding first, then primary, etc — same decision engine the Training page uses, not a duplicate), so the program actually changes over time instead of being locked in. Shown on the Player Advisor as a program timeline + a full week-by-week badge grid (`weeklyPrograms` array, `TRAINING_PROGRAM_SHORT_CODE` for the compact labels) + final skill table — youth get "Development plan to age 20", seniors/aging get a shorter 2/1 age-year outlook. The old "single program locked in for the whole horizon" comparison grid (`buildTrainingPotentialGrid`) was removed in v8.5 — nobody actually trains one skill for months, it was misleading as a comparison. Fatigue is NOT dynamically modeled (week 1 uses real fatigue, week 2+ assumes a healthy baseline of 8) — no match schedule to drive real fatigue dynamics, documented in the UI, not a bug. Known gap, not modeled (flagged in UI for age 29+, no fabricated number): the workbook notes skills actively DECLINE weekly from age 30 (not just train slower), doubling at 31, endurance declining 2x other skills — real per the workbook's own annotation but no exact rate was found, so long-horizon senior/aging projections likely overstate outcomes.
- Player Detail Advisor (`player.htm` — keep/release verdict for any single player, squad-peer comparison for 21+, adaptive training plan for every age) — **unverified against live markup, see gotcha**: `scrapePlayerDetailPage()`, `comparePlayerToSquadPeers()`, `simulateAdaptiveTrainingPlan()`, `updatePlayerAdvisor()`. `comparePlayerToSquadPeers()` is now also called from `updateTransferAdvisor()` (v8.8) for every 21+ transfer search result, not just the single player.htm page — shows which current squad player(s) a candidate would outrank/replace directly in the results list.
- Page routing: `detectPageType()`
- Caching: `_saveCache` / `_loadCacheWithAge` (GM_setValue/GM_getValue), staleness constants at top
- Squad parsing: `parsePlayerRow()` (own squad, full skill grid, `squadViewId=2`) vs `parseOpponentPlayerRow()` (opponent squad, reduced columns, `squadViewId=2` — see gotcha) vs `parseSummaryViewBlock()`/`scrapeSummaryView()`/`fetchSquadSummaryView()` (`squadViewId=1` — the ONLY view with Talents, for both own squad and opponents; different DOM shape entirely, `<div class="padded senior|youth">` blocks not `<tr>`). `mergeTalentsIntoPlayers()` combines the two views' data. Both `fetchAllData()` (own squad) and `fetchOpponentSquad()` now fetch both views. `fetchSquadSummaryView()` retries once on any failure (v8.8) — Talents live ONLY in this view, and a single dropped request used to silently wipe every player's talents for that refresh (see gotcha below). Both `fetchAllData()` and `fetchOpponentSquad()` also seed talents from the last known-good cached fetch before merging, so a fetch that fails even after the retry doesn't erase previously-known talents.
- Transfer scouting: `evaluateTransferTarget()`, `calculateRank()`, `checkScoutBenchmark()`. Primary-skill detection goes through `getPrimarySkillInfo(player)` (v8.10) — previously all three hardcoded `primary = Math.max(batting, bowling)`, so a genuine wicketkeeper prospect (strong keeping, modest bat/bowl) was judged on batting/bowling and filtered out regardless of keeping quality. Keeping now counts as primary once it's Average(4)+ and is actually the player's best discipline, matching the keeper-detection convention already used by training (`getYouthPrimarySkillName`) and tactics (`_detectPlayerContext`). **Senior (21+) hard filter had a live zero-results bug (fixed v8.11)**: `seniorMinChecks` in `evaluateTransferTarget()` checked `player.experience` unconditionally, but experience is always `0` on every transfer-list row until a per-player page fetch fills it in (same class of bug the "known" gate on `checkScoutBenchmark`'s Experience/Rating checks already exists to prevent — this second hard-filter block just never got the same gate). Every 21+ candidate failed Experience 0 < min(4/5) and was marked 'poor' before "Fetch Experience & Wages" was ever clicked, so the senior results list was always empty on first load regardless of squad or search filters. Now gated on `known: (player.experience || 0) > 0`, matching the pattern used everywhere else in the file that deals with post-fetch-only fields. **v8.12**: applied the same `known: value > 0` gate to Primary/Technique/Fielding/Endurance in `checkScoutBenchmark()`, the youth curve check, and `seniorMinChecks` — a real 0 across the board on a candidate almost always means that column failed to scrape/map (`_mapTransferHeader`/`parseTransferRow`), not a genuine Atrocious rating, and was silently hard-failing every candidate the exact same way the Experience bug did. Also added a `[FTP Transfer]` console.log funnel summary (scanned/pass counts split youth vs senior, plus sample failure reasons when a whole age group is wiped) — if a results list ever goes fully empty again with no obvious cause, check that log first instead of re-reading this scoring code from scratch. **v8.13**: `getPrimarySkillInfo()` was only wired into the hard-filter/verdict functions in v8.10 — three other places still computed `Math.max(batting, bowling)` directly and needed the same fix: `computeSquadStats()` (feeds the "candidate vs squad avg primary" bonus — a keeper on your own squad was dragging avgPrimary/minPrimary down using their bat/bowl instead of their keeping), `generateSeniorSellList()` and the youth sell list's post-20 fallback (both could flag a genuine squad keeper for sale based on mediocre batting/bowling), and the Player Advisor verdict line's cosmetic Bat/Bowl label (player.htm).
- Tactics: `calculateBattingScore()`, `calculateBowlingScore()`, `recommendLineup()`, `allocateBowlingSpells()`, `recommendTossDecision()`. `recommendBattingOrder(lineup, context)` is format-aware — T20 uses aggressive tactics for positions 4-11 (middle/death overs), OD uses Defensive anchor at #3 and Normal middle order. `allocateBowlingSpells()` now applies opponent analysis adjustments (pitchVulnerability, isFatigued, specialist-batter weakness) to bowling scores, consistent with `recommendLineup()`'s post-hoc adjustments.
- Training: `recommendTraining()`, `scrapeTrainingPage()`. Youth staging in `_recommendYouthTraining()` (v8.7): Fielding to **Reliable (7)**, not Capable (6) — then Technique (bowling/batting) to Reliable as its own mandatory stage before the primary skill, not just a catch-up when it lags. Sourced from a real experienced user's stated training order for a 16yo bowler ("fielding to reliable, then bowling technique, then bowling") — a genuine community-informed correction, not derived from the Excel workbook. Keeper skips the technique stage since Keeper-Batting already trains technique alongside keeping. **v8.17 exceptions**: Gifted (Fielding) lowers the fielding target to Capable(6) instead of Reliable(7) — it trains fast enough as a secondary that the extra tier isn't worth the dedicated time. Gifted (Technique) skips the dedicated technique stage entirely (same reasoning) and goes straight to the primary skill. Prodigy youths under 19 with both batting/bowling ≥3 get routed to All-rounder training instead of a single discipline — Prodigy's "all skills faster" applies to breadth, not just one skill, so building both early (then specialising after 18) captures more of the bonus while it's active.
- UI: `createPanel()` (shared component lib) + `addCommonStyles()`; each game page has its own `createXUI()` / `updateXAdvisor()` pair
- Confidence scoring: `computeConfidence(opts)` returns `{ level, label, score, reasons[] }` based on data freshness (cache age), skill completeness (playersWithSkills/totalPlayers), context info (academy, finance, opponent, match type). `renderConfidenceBadge(conf)` renders a color-coded stat badge. Wired into training page, tactics page, and transfer advisor section headers.
- Match schedule integration: `fetchUpcomingFixtures()` — background-fetches `teamfixtures.htm`, parses next 3 upcoming matches with format (T20/OD/YT20/YOD), returns `{ date, matchDate, matchClass, teams, format }[]`. Used by training advisor to show upcoming match context + format-specific training tips (e.g., "T20 coming up — prioritise power batting & short bowling spells"). Injected as an info alert at top of training recs container.
- Opponent danger report: surfaced in toss section of tactics page when opponent has `dangerousBowlerCount > 0` — lists dangerous bowler names and warns to prepare lower order. Also shows opponent form alert when `opponentAnalysis.inForm` is true.
- Match-week rest recommendations: when a match is within 3 days, the training page shows danger alerts for severely fatigued players (Listless or worse) recommending Rest to recover before the match. 7-day window triggers milder warnings for Exhausted/Shattered players.
- Enhanced opponent scouting: club dashboard opponent cards now show full analysis (strength classification, avg experience/form/fatigue, bowling breakdown, tactical insights, dangerous bowler names) instead of just player count and staleness.
- Transfer settlement: info alerts in senior and youth sell lists explaining settlement rules (listing fee $1,000, 50%+ for <100 days, 100% for 100+ days, youth recruits exempt from 7-day relist wait).

## Known gotchas
- **Opponent scouting could show your OWN team as "the opponent" (fixed v8.20)**: `getOpponentTeamId()` and `extractOpponentTeamIdFromGame()` both blindly treated the "Home" row in match details as the opponent. That's wrong whenever your own team has home advantage — "Home" is then literally your own team, and every downstream consumer (club dashboard opponent cards, tactics page opponent analysis) would scout, cache, and display your own squad as if it were the opposition. Fixed by checking both Home/Away rows and returning whichever one isn't `TEAM_ID`. Also added a one-time `cleanupOpponentCache(TEAM_ID)` call in `init()` to purge any stale self-keyed cache entry the old bug already saved, plus a defensive filter on the club dashboard's opponent list so a bad entry can't display even if cleanup somehow missed it.
- **Tactics recommendations flapping between visits with no real squad/opponent change (fixed v8.8)**: the Match Orders page force-refreshes the full squad on every visit (`pageType === 'orders'` sets `forceRefresh = true` in `init()`, intentionally — tactics should never run on hours-stale data). But that refresh fetches `squadViewId=1` (Talents) via `fetchSquadSummaryView()`, which used to silently `resolve([])` on ANY failure (timeout/non-200/parse error) with no retry — `mergeTalentsIntoPlayers()` then had nothing to merge, and every talent-driven score bonus (Prodigy/Skilled/Seam-Spin-Specialist/triggered talents) silently vanished for that refresh, changing the recommended XI purely from network flakiness, not a real game-state change. `recommendLineup()`/`calculateBattingScore()`/`calculateBowlingScore()` etc. are otherwise fully deterministic (no `Math.random`) given identical player data — the bug was entirely in the data layer, not the scoring logic. Fixed with a one-shot retry in `fetchSquadSummaryView()` plus a "seed from last known-good cache" fallback in both `fetchAllData()` and `fetchOpponentSquad()`, so a fetch that still fails doesn't erase talents that were already known from a prior successful refresh.
- `parseTransferRow()` (transfer search results) sets `wage: 0` and `experience: 0` — real values only arrive after a per-player page fetch. Never hard-filter on these without gating on `> 0` first, or every player fails and the results list goes empty.
- `AGE_SCOUT_THRESHOLDS` ("the base") is a **hard filter** in `evaluateTransferTarget`, not a scoring bonus. Values are taken verbatim from the user's saved Talent Scout search screenshots — treat them as source of truth, don't infer/interpolate/loosen without new screenshot data.
- Opponent squad pages (`seniors.htm`/`youths.htm?teamId=<other team>`) expose a genuinely different, reduced column set than your own squad page: Age/BT/Experience/Fatigue/Form/Wage/Rating only — no batting/bowling/technique/power/keeping/fielding/captaincy. This is the game's own scouting limitation, not a scraping bug. `fetchSquadFromPage()` auto-picks `parsePlayerRow` vs `parseOpponentPlayerRow` per row via `td.skills` count — don't reuse the own-squad column mapping for opponent data.
- No headless/authenticated access to fromthepavilion.org — if a fix depends on real page markup, ask the user for a raw HTML snippet rather than guessing selectors.
- `scrapePlayerDetailPage()` (player.htm) was written by extending `fetchPlayerPageDetails()`'s already-proven th/td label scan to the rest of the skill grid, **without** a live HTML sample of player.htm itself to confirm against — lower confidence than everything else in this file. It self-checks (`hasFullSkills`, needs 5+ matched skill labels) and shows a warning instead of a false verdict if scraping comes back empty. The user shared a screenshot in v8.1 confirming the visible field *labels* (Batting/Bowling/.../Fatigue/Form/Experience/Captaincy, all "Label: Value" rows matching what the code expects) — real corroboration, but a screenshot proves rendered output, not actual DOM/selectors. If the user reports it's not working, ask for the page's raw HTML before guessing at new selectors.

## Talents — verified against the official game manual
Source of truth is `rules.htm?rulespage=playerother` (fetched directly, not community-sourced) — quote it again before changing any talent logic, don't re-derive from memory.
- **Prodigy is youth-only.** Manual: "Trains faster in all skills while in the youth squad." Gifted (X) talents have no such restriction. Fixed in `estimateWeeklyTrainingGain()` (training math) and `evaluateTransferTarget()`'s senior branch (scoring — Prodigy now gives zero score bonus once senior, was previously +1).
- **Seam Specialist / Spin Specialist are BATTING matchup talents**, not bowling-boost talents. Manual: "performs better than normal when batting against seam/spin bowlers." Was misapplied in `calculateBowlingScore()` as a bonus to the player's own seam/spin bowling — removed. Correctly applied in `recommendLineup()` (post-hoc, alongside the existing `pitchVulnerability` adjustment) conditioned on `opponentAnalysis.seamerCount`/`spinnerCount` — i.e., only rewarded when the OPPONENT actually bowls more of that type. Also gated by `primaryName === 'batting'` (or `batting >= bowling` in the youth branch) in `evaluateTransferTarget`, since a pure bowler having this talent is dead weight.
- **New Ball Bowler/Old Ball Bowler/Opener/Finisher** were already correctly directional — confirmed against manual verbatim, no change.
- **Safe Hands** (fielding/keeping match bonus) — confirmed correct name and effect against manual, no change.
- **Triggered talents were entirely unhandled before this pass**: Wrongun, Flipper, Swing, Bouncer, Yorker, Slower Ball, Arm Ball, Doosra (bowling, in `calculateBowlingScore`) and Accumulator, Boundary Hitter (batting, in `calculateBattingScore`). Manual confirms each is real ("particularly skilled at bowling a ...") but does **not** quantify the effect size — the bonuses added are a conservative flat estimate (roughly half the size of the quantified Skilled-talent bonus), explicitly better than continuing to ignore a real talent, but not officially verified magnitude. If the user finds evidence of the actual size (forum/community testing), update these first.
- **Skilled (X) series**: manual confirms these exist and give a match bonus but, like triggered talents, never quantifies the size. The script's existing flat +5/+7 (format-aware) values are unverified estimates, not manual-sourced — worth flagging if revisited, but left as-is since they were already in place before this pass and no better source was found.
- **CORRECTION (v8.6): opponent talents ARE available — the earlier gotcha here was wrong.** `squadViewId=2` (the grid view, used everywhere for the skill grid) never has Talents. But `squadViewId=1` ("Overall Summary") DOES expose a full Talents list via `span.popuphelp` (`title="Name|Description"`) for BOTH your own squad and opponents — confirmed against real HTML from both. `fetchOpponentSquad()` and the own-squad fetch in `fetchAllData()` now also fetch `squadViewId=1` in parallel and merge Talents in via `mergeTalentsIntoPlayers()`. **Bigger finding**: `parsePlayerRow()` (the grid parser) never populated `player.talents` at all, meaning every talent-scoring function (Prodigy/Skilled/Seam-Spin-Specialist/triggered talents, all verified against the manual above) was running on an empty talents array for the user's OWN squad during real tactics recommendations — the scoring logic was correct, the data feeding it was silently missing. Now fixed. `analyzeOpposition()` exposes `oppSeamSpecialistBatters`/`oppSpinSpecialistBatters`/`dangerousBowlerCount`/`dangerousBowlerNames` from real opponent talent data; `recommendLineup()` uses the specialist-batter counts to lean bowling selection toward whichever type the opponent's own talent investment didn't cover. `dangerousBowlerNames` (Yorker/Bouncer/Swing/etc opponents) is now surfaced in the tactics advisor toss section (v8.16) — shows dangerous bowler count + names + warning to prepare lower order.

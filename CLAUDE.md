# FTP Advisor

Single-file Tampermonkey userscript: `ftp-advisor_user.js` (~6100 lines, one IIFE). Tactical/scouting advisor for fromthepavilion.org (cricket sim). Team is auto-detected per install (`getTeamId()`) — not hardcoded to any one team/user. No build step, no test suite, no other source files. Public repo: github.com/Jadax/ftp-advisor.

## Active Rules
- Keep the script modular; never duplicate a helper — grep for existing functions before adding one.
- No extensive explanatory prose in responses; output code/diffs directly, short summary only.
- Everything lives in `ftp-advisor_user.js` — don't create new files unless explicitly asked.
- Comments: only non-obvious WHY (hidden constraint, workaround, source of a magic number). Never WHAT.
- After any edit, verify with `node --check "ftp-advisor_user.js"` — the only available sanity check (no test suite, no build step, no headless access to the live game).
- Don't re-read the whole file to get oriented — grep/Glob the sections below by name.

## Ship workflow
Public repo, installed by other people. After a change is verified:
1. Bump `@version` in the metadata block (top of file).
2. `git add -A && git commit -m "vX.Y: <what changed and why>"`.
3. `git push` (origin already configured).
Do this for every shipped change unless told otherwise — there's no separate release process.

The game shows age as years + a week count out of 14 (`"25.05"` in tables, `"25y5w"` in detail panels), NOT a base-10 decimal — `parseFloat("20.14")` reads 20.14 (14% into the year) when it's actually 14/14 = 21.0, a player who for scouting/training purposes has already turned 21. Every downstream `Math.round(player.age)` bracket check (age-scout thresholds, 16-20 curve, senior/aging training paths) is correct as-is once fed a true decimal age from this function — no separate rounding logic needed, JS's round-half-up already lands boundary weeks (7+/14) in the next age bracket.
- **Age MODEL — week-aware reads (v8.62)**: `parseGameAge` still yields the true decimal age; how each reader turns it into a bracket is now deliberate, via the shared helpers in the AGE MODEL block (right after `formatAgeDisplay`): `ageYears(age)` = `Math.floor` (the age the GAME displays: 16y13w reads as 16 — used for per-year TABLE lookups like `AGE_SCOUT_THRESHOLDS`, `YOUTH_DEV_CURVE`, `SENIOR_MINS_*`, price-history age bands, and "age N" labels), `ageFraction(age)` = weeks/14 progress, `isYouthAge(age)` = `age < 21` continuous (20y13w is unambiguously still youth), `interpAgeTableValue(table, age, field)` and `interpAgeSteps(age, steps)` for continuous interpolation. Key consequence: a 16y6w player is 16 for the scout base / youth curve (previously `Math.round` flipped them to 17 half a year early, failing the 17-row minimums), and training/rating/rank age multipliers now RAMP across the year between row values (16y5w trains marginally faster than 16y6w; exact-year values unchanged) instead of stepping. **These per-year-table lookups must use `ageYears`, never `Math.round`** — there are no remaining `Math.round(player.age)` sites (grep if you add one). `weeksToAge`/`weeksToAge20` subtract a `1e-9` guard before `Math.ceil` so an exact-week boundary player (e.g. 16y6w) gets exactly 50 weeks to 20, not a phantom 51st (float drift: `(20-16.42857)*14` computes to `50.00000000000002`). No end-switching needed: each bowler's overs stay on their original end and the per-end side budgets make the match's odd/even alternation come out exact. The bowler's total overs never changes, so per-bowler caps hold. A safety net verifies the rebuilt plan (no collisions, nothing out of range, no consecutive over numbers) and falls back to the valid un-split plan with a console.warn if anything is off — plus the existing display no-rest warning covers residual cases. Verified with `v861_test.js` (24 assertions: collision-free full 50-over coverage, end/parity consistency, no consecutive overs, EVERY 4+ over bowler bowls both sides, low-endurance SeamC 4/4) and a new `v861_formats.js` (24 assertions: under-resourced 5-bowler OD, Youth OD 40-over with rest checks, T20/YT20 confirmed the split pass does NOT run and stays one-spell-per-bowler). ## Security
- **All scraped text is HTML-escaped at the PARSER, not at render sites** (`escapeHtml()`, v8.27). This is load-bearing, not hygiene: player names are chosen by other users (the game has a Rename Player page) and this script reads pages full of other people's players (transfer search, opponent squads, youth recruit table), then interpolates those names into `innerHTML` at ~80 sites. The game renders names safely, so `.textContent` hands back the raw string — a player named `<img src=x onerror=…>` would then execute in the page's own origin on an authenticated session (able to list players, accept transfers, send mail as the user). Classic safe-source/unsafe-sink. Escaping is applied in the 5 name parsers, the 3 talent parsers, and the ground.htm class/pitch scrape — **add it to any new scrape point**; do NOT rely on remembering it at each render site. Player names are display-only (nothing compares/matches on them) and talent matching is ASCII regex (`/prodigy/i`), so entity-escaping is behaviour-neutral.
- No credentials are committed. The script stores only the user's own local prefs (team ID, debug flag) via `GM_setValue` — no API keys, tokens, or shared secrets are ever bundled. Keep it that way: never hardcode a shared key into a public userscript.

## Known gotchas
- **Youth-match eligibility must use the game's own squad classification, not our decimal age (fixed v8.27)**: the manual says "Only players aged 20 and under are eligible" (`rulespage=competitions`) and "all players turning 21 are moved from your youth squad and are promoted to your senior squad" (`rulespage=youthacademy`) — so a player still in the youth squad has by definition not turned 21. `recommendLineup`'s youth filter used `p.age < maxAge + 1`, and a player displayed as `"20.14"` parses via `parseGameAge()` to 20 + 14/14 = **exactly 21.0**, so they were dropped as a 21-year-old while the game still listed them as an eligible 20yo youth player — silently removing a legal player from the recommended XI. Now `p.isYouth === true` short-circuits to eligible. Squad membership is only ever used to INCLUDE (a 20yo sitting in the senior squad is still age-eligible and falls through to the age test). Anywhere else that gates on the 20/21 boundary, prefer the game's own flag over the derived float.
- **Player Advisor (player.htm) and Transfer Search could disagree on verdict for the same player (fixed v8.26)**: `getYouthPrimarySkillName()` (used by `evaluateYouthDevelopment()` — both the Player Advisor and the youth sell list) required `bowlerCategory !== 'none'` before ever treating bowling as primary, on top of comparing bowling vs batting. `getPrimarySkillInfo()` (used by transfer search's `evaluateTransferTarget`/`checkScoutBenchmark`/`calculateRank` since v8.10) has no such dependency — pure skill-number comparison. Whenever bowlerType/bowlerCategory failed to scrape on a given page (scrapePlayerDetailPage's bowlerType span/regex fallback doesn't always match — see its own lower-confidence note below), a genuine bowler with bowling clearly ahead of batting fell through to being judged as a batsman on that page only, while the same player's transfer-search evaluation (sourced from a different scrape) correctly judged them as a bowler — same person, opposite verdicts (RELEASE vs STRONG), depending only on which page happened to scrape bowlerCategory successfully. Fixed by making `getYouthPrimarySkillName()` delegate straight to `getPrimarySkillInfo()` — one shared implementation, can't diverge again. Also fixed: raw unrounded decimal ages (e.g. "16.428571428571427yo") were leaking directly into several UI templates that interpolated `player.age` without formatting — added `formatAgeDisplay()` (reconstructs the game's own "Yy Ww" format) and applied it everywhere age is shown.
- **Squad page could silently zero out cached skill data (fixed v8.25)**: `scrapeSquad()`/`init()`'s squad-page handler always parses the current page with `parsePlayerRow()`, which expects the grid view (`squadViewId=2`) — but the normal squad nav link (Club > Senior/Youth Squad) has no `squadViewId` param and defaults to the Overall Summary view (no skill columns at all). On that view every stat silently read as 0, and `parsePlayerRow()` also hardcoded `hasFullSkills: true` regardless of whether any `td.skills` cell actually matched, so nothing flagged it. The all-zero scrape then overwrote the real cached skill data via `savePlayerCache()` — every downstream page (pitch advisor, tactics, training) started computing off 0.0 ratings for the whole squad, with no visible error (this is exactly what produced the "pitch recommendations are all Sticky, Bat/Seam/Spin 0.0" report). - **UI polish pass (v8.24) — done blind, not visually verified**: warmed the neutral palette (`:root` in `addCommonStyles()`) off cool blue-grey toward soft stone/cream (surface/border/text CSS vars), bumped corner radius (10→12/6→8/4→5px) and snappied transitions (0.2s→0.15s, panel entrance 0.3s→0.22s) for a friendlier/quicker feel, plus a bit more card padding/line-height and a gold focus-visible outline on buttons. - **v8.43 — mismatched role-specific talents were silently dropped instead of explained, for most talents**: user asked for an audit of real transfer-market example cards.
